# Shader golden test

This integration test executes every one of the 18 preset graphs through three
independent paths and compares the actual pixels:

1. the pinned official Anime4K mpv-hook GLSL files are concatenated in preset
   order and executed by FFmpeg/libplacebo on Vulkan;
2. the extension's production WGSL classes run in Chromium WebGPU and are read
   back from an `rgba16float` texture;
3. the renderer's embedded FXC/DXBC package runs through the production D3D11
   pipeline and is read back from `R16G16B16A16_FLOAT`.

The input is a deterministic 96x54 RGBA8 line-art fixture generated by the
runner. It includes gradients, flat fills, a curved outline, one-pixel dark
lines, and a small high-frequency patch. All 18 presets are tested at 192x108.
In addition, AA, BB and CA run at 384x216 in every quality, making their second
official x2 pass satisfy the `OUTPUT / MAIN > 1.2` condition. Thus the suite
contains 18 normal comparisons plus nine explicit 4x schedule comparisons.
The same generated input file is passed to all three backends; there are no
separately reimplemented fixtures.

The independent reference is always regenerated from the checked-in files at
the Anime4K commit recorded in `native/third_party/anime4k/SOURCE_REVISION.json`.
Reference pixels are never generated from WGSL, HLSL, hashes, or canned
non-zero checks. Nothing is downloaded by the runner.

Before running Anime4K, the runner also sends the fixture through an identity
libplacebo pass and requires every RGBA16-UNORM channel to equal the RGBA8 input
times 257. This catches a color-range, transfer-function, or channel-order
change in the independent reference path.

## Requirements and command

- the local npm dependencies and Playwright Chromium (`npm ci` and
  `npm run test:e2e:install`);
- a built `Anime4K.Golden.exe` target;
- FFmpeg on `PATH` with the `libplacebo` filter and Vulkan support;
- a working WebGPU/Vulkan/D3D11 adapter.

From the repository root, for the Ninja build layout used by the native build:

```powershell
python tests/golden/run_shader_golden.py `
  --native-exe native/build/bin/Anime4K.Golden.exe `
  --report artifacts/shader-golden-report.json
```

For a Visual Studio multi-configuration build, use
`native/build/bin/Release/Anime4K.Golden.exe`. Add `--warp` only for a D3D11
software diagnostic; the official GLSL and WebGPU paths still require their
normal GPU backends.

Scratch files are restricted to `.tmp`. The schema-2 JSON report records every metric,
the fixture and manifest hashes, the official source revision, and per-preset
combined-shader SHA-256 hashes. The oracle also asserts that A+A, B+B and C+A
remain distinct from their single-stage counterparts, so a hook loader cannot
silently deduplicate repeated graph invocations.

## Numeric acceptance

RGB values are clamped to the displayable [0,1] range before comparison because
the official oracle is read back as RGBA16 UNORM while the two production
backends use RGBA16F intermediates. Alpha is not part of Anime4K model quality.

Each backend versus the official GLSL oracle must meet all of:

- 7x7 Gaussian luminance SSIM (sigma 1.5) >= 0.985;
- RGB RMSE <= 0.035;
- 99th-percentile absolute RGB error <= 0.13.

The direct WebGPU-versus-D3D11 comparison is intentionally tighter:

- SSIM >= 0.995;
- RGB RMSE <= 0.015;
- 99th-percentile absolute RGB error <= 0.07.

The current schema-2 report deliberately remains failed rather than waiving a
limit: 26 of its 27 comparisons pass. `AA/M` at 4x is the sole failure, and it
misses only the unchanged official-oracle p99 gate (`0.1323287` for WebGPU and
`0.1323280` for D3D11, versus `0.13`). Its official-oracle SSIM and RMSE both
pass. The two production backends are nearly bit-identical in that same case
(`0.9999935` SSIM, `0.000174` RMSE and `0.000488` p99), which rules out a
WebGPU/D3D graph, weight, intermediate-range or tensor-layout mismatch. The
remaining Vulkan/libplacebo-versus-compute edge difference is recorded as an
unresolved acceptance failure; neither the fixture nor any threshold is tuned
around it.

Maximum absolute error is also reported but is not a gate: isolated pixels on
high-contrast edges can differ more because GLSL/Vulkan, WGSL/WebGPU and
HLSL/D3D11 do not promise identical sampler rounding. SSIM, RMSE and p99
together prevent a small set of edge samples from hiding a structural,
systematic, or widespread regression. In particular, FP16/min-precision CNN
accumulation is not acceptable: it was measured well below the SSIM gate and
was removed in favor of FP32 arithmetic.

The limiting AA/M preset was inspected before fixing these budgets. Of 62,208
RGB channel samples, only 568 (0.913%) exceeded 0.13 in D3D11 versus the GLSL
oracle, and all 285 affected pixels were within two output pixels of a local
contrast step greater than 0.1. Outside that two-pixel edge neighborhood, the
D3D11/oracle RMSE was 0.00115 and p99 absolute error was 0.00050. The direct
WebGPU/D3D11 comparison had SSIM 0.997535 and its over-gate samples were likewise
localized to the deliberate line/checker edges and clamp boundary. This is the
expected sampler-rounding shape, not a channel/tensor-layout or model-order
error. The source formats and shared manifest/preset graph independently guard
those invariants.

As a negative regression check, an experimental `min16float` CNN accumulator
build produced D3D11/oracle SSIM values as low as 0.888115 and visibly failed
the same fixed gates. Generated-shader unit tests also reject `min16float`, so
future performance work cannot silently trade away model fidelity.
